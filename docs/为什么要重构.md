# 为什么要重构 ttlock Flutter SDK

---

## 一、现有 SDK 的主要问题

### Dart 层

#### 1. 回调式异步，不符合 Flutter / Dart 习惯

业务侧往往要包一层 `Completer` 才能当 `Future` 用，可读性与错误处理都差。

```dart
static void initLock(
  Map map,
  TTLockDataCallback callback,
  TTFailedCallback failedCallback,
) {
  invoke(COMMAND_INIT_LOCK, map, callback, fail_callback: failedCallback);
}
```

---

#### 2. 部分接口入参、返参用 `Map`，契约不清晰

同一类能力（如初始化锁）在类型上无法自描述，IDE 补全弱，运行时才发现 key 拼错或类型不对。

```dart
static void initLock(
  Map map,
  TTLockDataCallback callback,
  TTFailedCallback failedCallback,
) {
  invoke(COMMAND_INIT_LOCK, map, callback, fail_callback: failedCallback);
}
```

---

#### 3. 枚举在三层各自定义，仅靠 `index` 对齐

Dart、Flutter 插件原生层、底层 SDK 各有一套枚举；**任意一层增删或调整顺序都会导致错位**，属于典型脆弱集成。

```dart
enum TTGatewayError {
  fail,
  wrongWifi,
  wrongWifiPassword,
  wrongCRC,
  wrongAeskey,
  notConnect,
  disconnect,
  failConfigRouter,
  failConfigServer,
  failConfigAccount,
  noSim,
  invalidCommand,
  failConfigIp,
  failInvalidIp,
}
```

---

#### 4. `command` + 巨型 `switch`，维护成本高

按命令字分支，回调类型与数据结构全靠约定，新增命令时容易漏分支或配错 callback 类型。

```dart
switch (command) {
  case COMMAND_GET_BLUETOOTH_STATE:
    int stateValue = data[TTResponse.state];
    TTBluetoothState state = TTBluetoothState.values[stateValue];
    TTBluetoothStateCallback stateCallback = callBack;
    stateCallback(state);
    break;

  case COMMAND_START_SCAN_LOCK:
    TTLockScanCallback scanCallback = callBack;
    scanCallback(TTLockScanModel(data));
    break;

  case TTGateway.COMMAND_START_SCAN_GATEWAY:
    TTGatewayScanCallback scanCallback = callBack;
    scanCallback(TTGatewayScanModel(data));
    break;

  case TTRemoteKey.COMMAND_START_SCAN_REMOTE_KEY:
  case TTRemoteKeypad.COMMAND_START_SCAN_REMOTE_KEYPAD:
  case TTDoorSensor.COMMAND_START_SCAN_DOOR_SENSOR:
    TTRemoteAccessoryScanCallback scanCallback = callBack;
    scanCallback(TTRemoteAccessoryScanModel(data));
    break;

  // … 更多 COMMAND_* 分支
}
```

---

### Android / iOS 原生层

| 现象 | 说明 |
|------|------|
| **单模型承载一切** | 入参集中堆在 `TTLockModel`（或等价物）里，字段语义混杂、难以演进。 |
| **单文件承载一切** | 逻辑集中在 `TtlockFlutterPlugin` 等超大类中，难以分工与测试。 |

参考：`ttlock_flutter_premise` 中  
`android/.../model/TtlockModel.java` 与 `TtlockFlutterPlugin.java`。

---

### 整体（仓库与产品线）

**在线版与离线版长期双轨开发，分支几乎无法直接 merge**，重复劳动多、缺陷修复难以一次性同步。

---

## 二、重构后如何对应解决

### 1. 代码与接口形态

| 方向 | 做法 |
|------|------|
| **统一契约** | 使用 **Pigeon** 在 Dart、Android、iOS（及 **OpenHarmony**）侧生成同一套接口定义，减少 `Map` 与口头约定。 |
| **枚举** | 仍需要手动映射，但**单一真相来源**后，错位风险显著下降。 |
| **异步与结构** | 不再使用 callback + command 分发 |

---

### 2. 在线 / 离线「分支不兼容」

| 方向 | 做法 |
|------|------|
| **联邦式架构** | 与官方插件推荐的 **Federated Plugin** 一致，各实现分包、分仓维护，按需组合与发布。 |
| **原生侧对齐** | Android / iOS 以 **submodule** 接入；原生另有独立仓库，用 **main** 与 **premise** 分支区分在线 / 离线能力。 |
| **抹平差异** | Android 侧在协作下收敛参数差异；iOS 侧通过 **moduleAlias** 统一在线 / 离线包名，使两条业务线**能合并到同一套 Flutter 分支**。 |

---

## 三、小结

- **Dart**：回调 + `Map` + 三层枚举 + command `switch`，可维护性与类型安全不足。  
- **原生**：大模型 + 大类文件，不利于演进与协作。  
- **组织**：双分支独立开发 → 通过 Pigeon、联邦分包、submodule 与别名策略，把**接口、仓库边界、在线离线差异**拆开治理。

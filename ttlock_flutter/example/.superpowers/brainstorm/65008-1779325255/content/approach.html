方案设计 — 渐进式重构

遵循现有架构风格（Riverpod + freezed + go_router），增量改进

推荐

方案 A：保留现有 Provider 模式 + 通用扫描页

每个设备独立 Provider + Page + Model，共享一个参数化 ScanPage

Pros

  • 与当前架构一致，改动可控
  • 扫描页复用，避免重复代码
  • 每个设备边界清晰

Cons

  • Provider 数量较多
  • 配件状态需从锁页面协调
B

方案 B：统一设备抽象层

Device 基类 + DeviceProvider 聚合所有设备类型

Pros

  • 统一状态管理
  • Dashboard TabBar 数据聚合方便

Cons

  • 与现有代码风格差异大
  • 过度抽象，示例应用的复杂度不需要
  • freezed 联合类型维护成本高
C

方案 C：最小改动

仅在现有扫描页加类型选择，锁页面加配件入口

Pros

  • 改动量最小

Cons

  • 扫描页无法复用（配件场景硬编码）
  • 不解决持久化和命令 UI 问题
  • 治标不治本
